# Практические задания для изучения Garbage Collector в Java с четкими критериями контроля

## Задание 1: Создание и удаление объектов

**Требования:**
- Создать 100 000 объектов класса `MemoryConsumer` (собственный класс с полем `byte[] data = new byte[1024]`)
- Выполнить 3 итерации: 
  1. Без удаления объектов
  2. С присвоением ссылкам `null` через каждые 10 000 объектов
  3. С явным вызовом `System.gc()` после каждой 10 000 объектов
- Замерять использование памяти перед и после каждого этапа

**Критерии контроля:**
1. Разница в использовании памяти (MB) до/после GC
2. Количество выполненных сборок мусора (из логов)
3. Время выполнения каждого этапа (мс)
4. Наличие сообщений о сборке мусора в выводе

**Пример кода:**
```java
public class GCDemo {
    static class MemoryConsumer {
        byte[] data = new byte[1024]; // 1KB
    }

    public static void main(String[] args) {
        monitorMemory("Before allocation");
        
        // Этап 1: Создание без удаления
        List<MemoryConsumer> list1 = new ArrayList<>();
        for (int i = 0; i < 100_000; i++) {
            list1.add(new MemoryConsumer());
        }
        monitorMemory("After 100k objects");
        
        // Этап 2: Удаление через null
        List<MemoryConsumer> list2 = new ArrayList<>();
        for (int i = 0; i < 100_000; i++) {
            list2.add(new MemoryConsumer());
            if (i % 10_000 == 0) {
                list2 = null;
                list2 = new ArrayList<>();
            }
        }
        monitorMemory("After null assignment");
        
        // Этап 3: Явный вызов GC
        List<MemoryConsumer> list3 = new ArrayList<>();
        for (int i = 0; i < 100_000; i++) {
            list3.add(new MemoryConsumer());
            if (i % 10_000 == 0) {
                System.gc();
                monitorMemory("After GC at " + i);
            }
        }
    }

    static void monitorMemory(String stage) {
        Runtime rt = Runtime.getRuntime();
        long totalMemory = rt.totalMemory();
        long freeMemory = rt.freeMemory();
        System.out.printf("[%s] Total: %.2f MB, Free: %.2f MB, Used: %.2f MB%n",
                stage,
                totalMemory / 1048576.0,
                freeMemory / 1048576.0,
                (totalMemory - freeMemory) / 1048576.0);
    }
}
```

## Задание 3: Анализ логов сборки мусора

**Требования:**
- Запустить приложение с параметрами:
  `-Xmx100m -Xlog:gc*,gc+heap=debug,gc+age=trace:file=gc.log:time`
- Сгенерировать нагрузку, вызывающую как минимум 5 minor GC и 2 major GC
- Проанализировать логи с помощью скрипта

**Критерии контроля:**
1. Наличие в логах записей о:
   - Начале и завершении GC
   - Размере heap до/после
   - Длительности паузы
2. Подсчет количества:
   - [GC (Allocation Failure)] записей
   - [Full GC] записей
3. Расчет средней длительности паузы

**Пример обработки логов (Python):**
```python
import re

def analyze_gc_log(log_file):
    with open(log_file, 'r') as f:
        lines = f.readlines()
    
    # Поиск записей GC
    gc_events = [line for line in lines if 'GC pause' in line or 'GC concurrent' in line]
    
    # Извлечение времени пауз
    pause_times = []
    for line in lines:
        match = re.search(r'pauses: (\d+\.\d+) ms', line)
        if match:
            pause_times.append(float(match.group(1)))
    
    print(f"Total GC events: {len(gc_events)}")
    print(f"Average pause time: {sum(pause_times)/len(pause_times):.2f} ms if events > 0 else 'N/A'")
```

## Задание 4: Работа с различными типами ссылок

**Требования:**
- Создать 3 теста с разными ссылками:
  1. WeakReference - объект должен быть собран при следующем GC
  2. SoftReference - объект должен остаться до нехватки памяти
  3. PhantomReference - проверить очередь referenceQueue
- Принудительно вызывать GC после каждого этапа
- Ограничить heap до 20MB: `-Xmx20m`

**Критерии контроля:**
1. Для WeakReference:
   - Объект собран после первого GC
   - `get()` возвращает null после GC
2. Для SoftReference:
   - Объект остается после нескольких GC
   - Объект удаляется только при нехватке памяти
3. Для PhantomReference:
   - Объект помещен в очередь referenceQueue
   - `get()` всегда возвращает null

**Пример кода для WeakReference:**
```java
public class WeakReferenceDemo {
    public static void main(String[] args) {
        Object target = new Object();
        WeakReference<Object> weakRef = new WeakReference<>(target);
        
        System.out.println("Before GC: " + weakRef.get());
        target = null;
        System.gc();
        // Даем время GC завершиться
        try { Thread.sleep(100); } catch (InterruptedException e) {}
        
        System.out.println("After GC: " + weakRef.get()); // Должно быть null
    }
}
```

## Задание 5: Создание искусственной утечки памяти

**Требования:**
- Создать класс с утечкой через статическое поле
- Запустить с `-Xmx50m`
- Добавлять объекты до `OutOfMemoryError`
- Сделать heap dump при ошибке: `-XX:+HeapDumpOnOutOfMemoryError`

**Критерии контроля:**
1. Heap dump должен показывать:
   - Статическое поле как root-объект
   - Большое количество недостижимых объектов
2. В VisualVM/MAT:
   - Dominator Tree должен указывать на утечку
   - Path to GC Roots должен показывать цепочку ссылок
3. Размер heap должен расти до 95%+ перед OOM

**Пример кода с утечкой:**
```java
import java.util.ArrayList;
import java.util.List;

public class MemoryLeakDemo {
    static List<String> cache = new ArrayList<>();
    
    public static void main(String[] args) {
        try {
            for (int i = 0; ; i++) {
                cache.add("Leak " + i + " " + "x".repeat(1000));
                if (i % 1000 == 0) {
                    System.out.println("Added " + i + " items");
                }
            }
        } catch (OutOfMemoryError e) {
            System.out.println("OOM after " + cache.size() + " items");
            throw e;
        }
    }
}
```

**Критерий успешности:** В MAT должен быть обнаружен путь от GC Roots к утечке через `MemoryLeakDemo.cache`.

## Задание 6: Эксперимент с finalize()

**Требования:**
- Создать класс с переопределенным `finalize()`
- Создать 10 000 объектов этого класса
- Запустить GC и замерить время до вызова finalize()
- Сравнить с использованием PhantomReference

**Критерии контроля:**
1. finalize() должен:
   - Вызываться не сразу после GC
   - Выполняться в отдельном потоке
   - Увеличивать общее время работы программы
2. PhantomReference:
   - Должен обрабатываться быстрее
   - Не блокировать основной поток
3. Замеры времени:
   - finalize(): > 100ms задержка
   - PhantomReference: < 10ms

**Пример кода:**
```java
public class FinalizeDemo {
    @Override
    protected void finalize() throws Throwable {
        System.out.println("Finalize called at " + System.currentTimeMillis());
    }

    public static void main(String[] args) {
        long start = System.currentTimeMillis();
        
        for (int i = 0; i < 10_000; i++) {
            new FinalizeDemo();
        }
        
        System.gc();
        System.out.println("GC requested at " + System.currentTimeMillis());
        
        // Даем время на обработку
        try { Thread.sleep(2000); } catch (InterruptedException e) {}
        System.out.println("Total time: " + (System.currentTimeMillis() - start) + "ms");
    }
}
```

## Задание 7: Настройка параметров кучи

**Требования:**
- Провести 3 эксперимента с разными параметрами:
  1. `-Xms64m -Xmx64m -XX:NewRatio=2`
  2. `-Xms64m -Xmx64m -XX:NewRatio=8`
  3. `-Xms64m -Xmx64m -XX:SurvivorRatio=2`
- Замерить:
  - Количество minor GC
  - Время выполнения
  - Размер Eden/Survivor space

**Критерии контроля:**
1. При увеличении NewRatio:
   - Уменьшение размера young generation
   - Увеличение количества minor GC
2. При уменьшении SurvivorRatio:
   - Увеличение размера Eden space
   - Уменьшение количества minor GC
3. Изменение размеров областей памяти должно соответствовать расчетам:
   - Eden = (NewSize * SurvivorRatio) / (SurvivorRatio + 2)

**Пример анализа памяти:**
```java
public class HeapParamsDemo {
    public static void main(String[] args) {
        MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();
        for (MemoryPoolMXBean pool : ManagementFactory.getMemoryPoolMXBeans()) {
            System.out.println(pool.getName() + " - Usage: " + pool.getUsage());
        }
        
        // Генерируем нагрузку
        List<byte[]> allocations = new ArrayList<>();
        for (int i = 0; i < 1000; i++) {
            allocations.add(new byte[1024 * 100]); // 100KB
            if (i % 100 == 0) System.gc();
        }
    }
}
```

**Критерий успешности:** При изменении SurvivorRatio с 8 до 2 должно наблюдаться уменьшение количества minor GC на 15-25% при одинаковой нагрузке.
